General property sets

Page 3 of 56 - Getting Started

This section describes how information is structured and captured within a BIM model using Property Sets (Psets). Property Sets are standardised containers used to group related information and ensure consistent assignment of attributes across multiple elements. They enable designers to efficiently apply shared properties, such as material characteristics or performance parameters, during early design stages.

As the project progresses into construction, information requirements become more detailed and element-specific. For example, concrete elements may require pour-level data, and manufactured products may require information linked to specific suppliers or production batches. At this stage, the high-level information captured in Psets is refined into more granular data to support fabrication, installation, quality assurance, and handover requirements. This refinement does not necessarily require decomposition into individual elements, but rather a more precise allocation of data where needed.

During early design, a relatively large volume of generalised information is captured. This information often applies across multiple element types and forms the basis for structural assumptions, design intent, and performance criteria.

During construction, the overall volume of newly introduced information typically decreases, but the level of detail increases. The focus shifts toward maintaining design intent while incorporating verified as-built information. It is important to preserve high-level design data while adding or updating element-specific details such as manufacturing tolerances, installation variations, material batches, and supplier information to ensure the model accurately reflects the constructed asset.

Information captured at different project stages should remain traceable and consistent throughout the BIM lifecycle. Where properties evolve from design intent to as-built condition, both versions should be managed in a controlled manner to avoid loss of design rationale or ambiguity in the final record model.

In practice, the required information is often distributed across multiple IFC property sets, which can make it difficult to manage and interpret at the element level. To address this, IfcPropertySetGroup can be used to logically organise related property sets under a single named grouping.

IfcPropertySetGroup is an IFC concept that allows multiple property sets to be associated through a common grouping mechanism. Rather than creating new or duplicated property sets, existing Psets are referenced and organised into a structured collection that represents a coherent information set.

How IfcPropertySetGroup works

1. Define the group entity

  • Create an instance of IfcPropertySetGroup.

  • Assign a meaningful name, for example: ConcreteElementPerformance.

2. Reference multiple property sets. The group aggregates existing property sets such as:

  • Pset_ConcreteElementGeneral
  • Pset_MaterialCommon
  • Pset_MaterialMechanical
  • Any relevant project-specific or custom Psets

3. Assign the group to an element or type

  • Use IfcRelAssociates (or the appropriate relationship entity depending on implementation) to link the group to an IfcElement or IfcTypeObject.
  • This enables a single logical reference point that connects all related property sets.

Limitations of IfcPropertySetGroup

  • Support for IfcPropertySetGroup is not consistent across all IFC authoring tools and viewers.
  • Implementation may require custom export mapping or transformation logic depending on the software used.
  • Downstream systems may still need to resolve grouped Psets into individual property sets for full compatibility.

note

The Record column indicates whether a property set should be captured at design stage, construction stage, or both. Where a property set is marked for construction only, it should not be assumed or populated during early design unless required for coordination.

Property set names in the table follow IFC naming conventions. Custom or project-specific extensions should use a clear prefix or suffix so they can be distinguished from standard Psets during export and validation.
